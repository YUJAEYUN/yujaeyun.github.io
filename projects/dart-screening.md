# DART 영업 대상 법인 스크리닝

![Type](https://img.shields.io/badge/Type-Internal%20Tool-purple) ![Status](https://img.shields.io/badge/Status-운영%20중-success) ![Period](https://img.shields.io/badge/Period-2026.03~현재-blue)

**Tech Stack:** Python, DART OpenAPI, XBRL, LLM

---

## Problem

영업이사님이 부서의 금융상품을 제안할 영업전략을 세우고, 그 조건을 만족하는 법인을 찾고 있었습니다. 상장법인 3,950곳의 사업보고서 재무제표를 하나씩 열어 확인하고 엑셀로 종합해야 했고, 대리님들이 나눠 맡아도 며칠이 걸렸습니다. 리서치팀에 의뢰하는 방법도 있었지만 회신까지 시간이 걸렸고, 받은 목록이 실제 영업으로 이어진다는 확신도 없었습니다.

DART OpenAPI로 스크리닝 코드를 만들자 재무제표 항목 조건은 빠르게 처리됐습니다. 문제는 영업전략이 바뀌며 OpenAPI가 제공하지 않는 값, 예를 들어 통화별 외화자산 보유액처럼 보고서 주석에만 있는 값을 찾아야 할 때였습니다. 정규식과 표 파싱만으로는 값이 누락되거나 전기 금액을 당기 값으로 잘못 읽는 오류가 났습니다.

---

## 구조

| 단계 | 하는 일 | 제한과 검증 |
|---|---|---|
| 규칙 추출 (코드) | 외화위험 관련 주석에서 해당 통화가 포함된 표와 주변 설명만 찾음 | 해당 통화가 없으면 LLM을 호출하지 않음 |
| LLM 판정 | 추려진 표와 단위·기간 설명을 함께 받아 당기말·연결 기준 금액을 추출 | 응답은 정해진 JSON 형식으로만, 코드가 형식을 검증 |
| 근거 기록 | 모든 값에 근거가 된 원문 위치와 값을 시트에 함께 남김 | 담당자가 결과를 그대로 믿지 않고 직접 확인 가능 |
| 검증 | 보유 사실이 알려진 기업이 결과에 포함되는지, 이전 버전과 교차검증 | 보고서 4만여 건을 검토하며 발견한 오류를 유형별 처리 규칙으로 반영 |

---

## 선택과 포기

| 선택한 것 | 포기한 것 | 그렇게 판단한 근거 |
|---|---|---|
| 애매한 값 판단을 LLM에 맡김 | 규칙만으로 처리해 호출 비용 줄이기 | 애매한 값을 전부 걸러내면 조건을 만족하는 법인을 놓치고, 전부 받아들이면 정합성이 무너짐 |
| 정형화된 부분은 규칙, 판단이 필요한 부분만 LLM | 전부 LLM에 맡겨 구현을 단순화 | 형식마다 정규식을 계속 늘리는 방식은 새 형식이 나올 때마다 다시 깨지고, 문장으로만 적힌 주석은 규칙으로 처리할 수 없음 |
| OpenAPI·XBRL·원문 다운로드를 조합 | 하나의 출처만 사용해 단순화 | 하나의 출처만으로는 법인마다 다른 명칭과 누락을 확인할 수 없음 |

법인마다 같은 항목을 다른 명칭으로 공시했고, 표 형식도 원화환산액을 함께 적는 형식·외화 원금만 적는 형식·계정과목별로 나누는 형식·표 없이 문장으로 적는 형식의 4가지로 나뉘었습니다. '(전기말)'처럼 소괄호로 기간을 표기한 표를 당기 표로 오인하거나, 한 보고서에 함께 들어 있는 연결·별도 재무제표를 섞어 읽는 경우도 있어 이런 함정을 유형별로 정리해 처리 규칙에 반영했습니다.

## 결과

- 며칠 걸리던 대상 법인 추출을 10분 안에 끝낼 수 있게 됐습니다 (상장법인 3,950곳 → 59곳).
- 이 스크리닝을 바탕으로 신규 법인을 유치했고, 4,000억 원 규모의 FX 거래가 성사됐습니다.
- 입사 한 달이 되기 전에 만든 도구라, 이후 영업전략이 잡힐 때마다 스크리닝 의뢰가 주기적으로 들어옵니다.

## 한계

표준화된 공시 형식이 없어 새로운 형식이 나올 때마다 처리 규칙을 추가해야 합니다. 지금은 조건별로 따로 만들던 스크리닝들을 하나의 설정 기반 에이전트로 통합해, 구현 내용을 몰라도 부서 누구나 쓸 수 있게 만드는 작업을 하고 있습니다.
